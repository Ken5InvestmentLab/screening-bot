# Switch completed finite recovery to ordinary New A acceptance

Finite recovery applies to one data date and one execution date. A successful
recovery does not authorize ordinary daily processing on the execution date
or any later date.

The existing normal launcher and scheduled activation check stay in place.
This transition requires an independent operator to establish both a complete
historical recovery and current, exact-version protected measurements.

1. Reconcile the archived terminal runner receipt with the independent D1
   and Discord readback using `finite_completion.verified_completion`.
   Use records from trusted operator storage. This reader only checks the
   archived facts and does not connect to D1 or Discord. It is specific to
   the recorded Nov17 recovery schema and cannot retire other admissions.
2. Establish the current release on the normal Worker origin. Use the
   ordinary release and live checks for the version, then obtain the actual
   protected owner document and API success, and the independent deny
   observations for anonymous and direct paths. Obtain the underlying
   receipts from authorized host readers. See
   [Worker response observations](new-a-owner-response-observation.md).
   Neither a public health response nor one role lookup is a protected
   response. The observation candidate is not a production host adapter.
3. Bind the real owner's reviewed decision to that exact release, current
   authentication files, previous acceptance, active overlay digest and
   reconciled recovery evidence. The operator needs the formal ordinary
   acceptance decision and a distinct finite-to-ordinary transition review.
   If the current owner message is in another chat, the same authenticated
   account must be independently verified. The trusted host supplies a fresh
   room-transfer observation bound to both exact messages, their digests, and
   rooms; the review binds that observation. A thread name, a copied message,
   or matching display names alone do not authorize the transfer.
4. Run `continuing_transition.prepare` with the independent readers. A
   successful plan cannot write activation. The trusted host issues the
   matching ordinary grant through `continuing_acceptance.issue`, then passes
   it to `continuing_transition.apply` with the same evidence sources and
   normal read-only launch preflight.
5. The application repeats the evidence checks under the existing task
   and daily locks, archives the prior bytes and the immutable review and
   claim, and compares the active digest before replacement. The only
   changes are the ordinary acceptance evidence and retirement of the
   finite overlay. The runtime validator requires the completed application
   record and historical predecessor evidence before admitting a later run.
   When an attempt has a claim but no completed record, reconcile the recorded
   before/after digests and current activation under the same locks. Do not
   delete its audit to reuse a grant or start daily processing.
6. Recheck the next target day's final and in-progress receipts with the
   ordinary launcher. Start a new scheduled run only when all regular
   prerequisites are true. Track the terminal run and its publication and
   notification receipts independently of the historical recovery.

These APIs are production-path candidates exercised in isolated temporary
repositories with injected trusted-reader fixtures. No standalone approval
JSON CLI or token-based fallback is provided. Deployment, host observation
provisioning and live application are separate operations. The candidate
cannot supply real measurements for a release on which it has not run, and
a source or Worker change requires measurements for the resulting release.
