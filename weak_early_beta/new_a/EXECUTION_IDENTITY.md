# Isolated V2 execution identity candidate

This implementation is not deployed and does not issue production acceptance.
It installs no provider, browser, credential or production-host adapter. Calling
the ordinary entry point without trusted V2 readers fails closed. V1 still
requires exact Git HEAD and cannot be upgraded from old evidence automatically.

V2 issuance requires a new genuine owner primary and host interpretation bound
to `NEW_A_CONTINUING_OWNER_ACCEPTANCE_V2`, its distinct decision and the exact
execution-identity digest. A newly observed exact-source deployment, normal
owner document/API success, anonymous/direct-route denials and their original
same-version/artifact receipts are also required. Local records are operator
attestations, not platform signatures. Synthetic fixtures have no production
authority.

The accepted anchor includes all tracked file paths, file modes and blob
identities. Each subsequent commit must be linear, touch only
`weak_early_beta/state/detections.csv`, retain the header, row count/order and
unique detection IDs, and append previously empty D6 receipt URL/time cells.
Only their corresponding `updated_at` can change. Unknown columns, other cells,
row changes, merges, executable-mode changes and receipt replacement/erasure
reject. Receipts must have a valid Discord message URL, timezone, nonfuture
timestamp, and the recorded D6 day when present. A code change followed by a
revert also requires fresh acceptance. Commit messages are never evidence.

Separate host readers must verify the existing nonsecret runner configuration,
fixed bootstrap/seed/calendar/history/presentation/quote hashes and runtime
environment. They must not read credentials or introduce a new loader. Daily
The runner metadata must describe the effective selected command/settings,
reference and loader precedence, DB binding and unchanged existing notification
destination identity; hashing a config path or an unused file is insufficient.
These metadata have not been obtained in production. Daily
mutable DBs, acquired prices, claims and results are not lifetime-pinned: the
existing source-quality, watermark, target-day, idempotency and external-action
guards remain in control of them on every run.

Every V2 validation requires an independent current Worker observation, at most
five minutes old, binding the normal production URL without overrides to the
actual response version, exact deployed source/artifact and one 100% deployment.
Old successful HTTP 200 or identical authentication files cannot replace this.
Initial response evidence has a separate one-hour issuance window and remains
immutable; it is not remeasured daily. The runtime and deployed source commits
are distinct: a proven append-only receipt commit can advance runtime HEAD while
the accepted Worker remains unchanged. A new Worker version/deployment/artifact
requires new genuine acceptance even if the code appears identical. HEAD,
cleanliness, dependencies and deployment are rechecked against observation
races; existing finite-grant/CAS/lock/application/revocation audits remain.

## Integration prerequisites

Production still lacks the trusted current actual-version/artifact observer and
the nonsecret existing-loader identity reader required by this API. No JSON-file
factory or command that turns assertions into these observations is supplied.
The existing isolated release-handoff candidate also needs to pass these readers
through issuance, finite application and runtime activation validation before
V2 can be introduced. It must preserve the known accepted operating combination
on missing/failed candidate evidence. The current daily runner creates a new
deployment tag after calculation; this is a real Worker-version transition and
must use the accepted-release handoff, not silently reuse the V2 certificate.

Consequently this isolated change does not authorize the pending Nov17 recovery
or repair current production acceptance. Introducing it requires a concrete
candidate release, genuine same-version observations through an allowed path,
explicit V2 owner intent, regular distribution/acceptance and normal launch
preflight/locks/side-effect reconciliation. Existing blocked observation paths
must not be retried or bypassed to supply those requirements.

## Reversion

The patch is additive V2 plus optional reader parameters; existing V1 behavior
and records are retained. Before any future rollout, retain the exact accepted
code/Worker/activation combination and immutable audit chain. Revert the local
candidate commit if it is not adopted; no production rollback is performed here.
If V2 were applied later, reverting source alone cannot reinterpret a V2 record
as V1: use the formal accepted-release transition and preserve its original
record/grant/application/revocation history. Never edit acceptance hashes or
delete failed claims to make an older release pass.
