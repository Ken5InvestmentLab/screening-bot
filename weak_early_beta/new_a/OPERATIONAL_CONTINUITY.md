# Finite Nov17 operational continuity

`NEW_A_OPERATIONAL_CONTINUITY_V3` is a separate, finite Nov17 recovery contract.
It preserves the old V1 activation, records and audit bytes. It does not make a
new owner HTTP measurement: `owner_http_observed` stays false. Management
deployment ID, traffic-percentage observation and final Worker artifact SHA are
also unmeasured; the prepared input digest is named accordingly.

The current trusted Codex user instruction and the host's source-bound review
authorize this alternative contract. Its evidence is an exact successful normal
tag CI release, Wrangler's unique Current Version ID, the actual normal public
health response's version-metadata ID/tag, source and prepared-input digest,
effective nonsecret authentication-policy digest, and two independent existing
D1 SELECTs bracketing that response. The challenge binds the response to a fresh
nonce. It returns no private data, identifiers or secret hashes, and writes no D1
rows. Existing owner/private authentication and notification qualification stay
unchanged. The only reviewed authentication-source delta adds that diagnostic
branch on the already public health path.

The existing loader determines effective configuration and actual Discord bot,
webhook and channel identities using existing read-only service authentication.
Credential values remain in memory. Its selection identity distinguishes true
inherited overrides from child inheritance of the same configured value. It pins
the fixed bootstrap inputs and runtime bytes; mutable daily data remain governed
by their existing source-quality and idempotency checks.

The activation's additional private reference is CAS-applied while holding the
normal task-entry and daily locks. It grants only target 2026-11-17 observed on
2026-11-18, for at most six hours. Daily requires the existing typed native
once-only continuation and its retained acquisition copy. Ordinary daily cannot
use this finite grant. Scoring and hypothetical trade rules are unchanged.

Because the code-only Worker was already deployed and verified, this finite
runner reuses that exact CI release instead of deploying the same code again.
It publishes calculation results only to D1. Before publication it requires the
original Nov16 revision3 pointer and saved publication receipt. After publication
it accepts revision4 only for this exact immutable run/bundle/snapshot. A lost
local publication receipt can be reconstructed from a verified identical active
dataset without another pointer CAS while the original root still owns its live
execution context. A terminal root requires a separately reviewed stage-only
handoff; it never authorizes replaying the full daily run. Notifications require the saved publication
receipt, verify the finite contract before staging and each send, and retain
per-message receipts and ambiguous-outcome reconciliation.

The V3 publication uses `operational_gate_continuity_verified: true` and
`existing_owner_gate_verified: false`. Successful completion keeps those distinct
in the runner receipt. Expiry, changed source/config/policy/version/D1/input,
unknown delivery, conflicting locks or a different date stop before the next
action. The normal 17:00 task definition and V1/V2 contracts are unchanged.

Recovery of code uses a new ordinary `cloud-deploy-*` release retaining the
CloudRoleAuthority export/binding/migration. No Dashboard rollback to a version
before that class, D1 schema replay, authority recreation or automatic resend is
part of this contract. Before D1 pointer publication the original revision3 data
stay active. After a partial publication reconcile the exact active dataset and
unsent outbox rows; never repeat detection or known successful delivery.
